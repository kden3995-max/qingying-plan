# 默认内存游客模式与后续账户方案

用户已明确授权完成并测试第一阶段；第二阶段仅方案。保留现有视觉、SPA、计算、健康限制与记录功能。本轮不推送、不发布。

## 当前实现与改动边界

`ui.js` 启动时使用 `features.js` 的 createStore 自动恢复 `qingying-state-v1`，每次资料／记录提交写 localStorage，storage 事件会合并其他页面的状态。第一阶段移除这些自动恢复、写入和合并路径。`app.js`、`features.js` 的计算、健康限制、备份格式和校验保持不变。

## 采用方式

采用当前 UI 闭包中的内存 state。未采用 sessionStorage（用户明确排除），也不为游客创建匿名云端账户。默认无登录入口，不接未配置的服务。

- 每次新文档进入、刷新或重新打开从空资料开始并显示首页。站内按钮与同一游客的浏览器前进后退仍保留当前内存草稿。
- 顶部持续显示游客提示和“结束体验并清空”，记录区保留同一操作。清空会清除全部内存、所有敏感 DOM 输出、输入草稿、图表、对话框和文件预览，返回首页；旧历史路由只会显示空数据。
- pagehide/freeze 同步清除并遮蔽敏感内容；pageshow/resume 重新初始化，在浏览器完成表单恢复后的下一任务再清理并解除遮蔽。避免 BFCache 恢复展示旧资料。浏览器原生表单恢复用 autocomplete=off 辅助，不能只依赖它。
- 每次清理递增体验代次；异步文件读取与确认导入必须属于当前代次，结束后不能重新出现旧预览或数据。
- 不使用 localStorage/sessionStorage/cookie/IndexedDB 保存游客资料，不上传游客数据。只有明确手动导出才生成备份文件。

## 旧数据管理

默认只枚举旧键是否存在，不读取 value、不解析、不展示条数或个人字段。通用提示不意味着这些数据属于当前游客。恢复按钮先显示不含健康数据的确认说明，确认后才读取、校验并替换当前内存；不自动合并、不上传、不保存回浏览器。旧副本保留，删除需要独立明确操作，且只删除旧键，不影响其他站点数据。读取／解析／删除失败保留现有游客状态和旧数据，明确提示。

## 失败与验收边界

更新内存先完整校验，失败不覆盖旧 state，不清掉用户输入。手动导入、导出错误可见。浏览器禁用存储不影响正常游客操作。测试真实跨文档返回与 BFCache（如环境可用）、重新打开、刷新、结束后后退、两个页面互不读取、旧数据确认、失败及异步读取跨体验竞态。

账户 A/B 的服务端访问隔离、真实退出、云端保存失败和登录过期需真实后端与两个用户，第一阶段不伪造验证。第二阶段提供后端、费用、RLS/服务端约束、会话清理与部署步骤，独立标明未实现。
